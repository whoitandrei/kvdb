# kvdb — мини key-value БД на C++ со своим thread pool

Учебный пет-проект: собственный thread pool, поверх него TCP-сервер, поверх
него — маленькая key-value база данных, по духу близкая к Redis.

## Идея и цель

Каждый слой в проекте написан вручную:

- **thread pool** — очередь задач + N воркеров, `mutex` + `condition_variable`;
- **TCP-сервер** — сырые системные вызовы (`socket`/`bind`/`listen`/`accept`/`poll`);
- **хранилище** — простой текстовый протокол и `std::unordered_map` под
  мьютексом.

Цель — разбор архитектурных решений и многопоточных
проблем.

## Стек

- **Язык:** C++20.
- **Сборка:** CMake ≥ 3.20, генератор Makefiles.
- **Тесты:** GoogleTest, подключается через `FetchContent`.
- **Санитайзеры:** ThreadSanitizer и AddressSanitizer как отдельные типы
  сборки.
- **Платформа разработки:** macOS (Apple Clang). Сетевой код опирается на
  POSIX-вызовы и должен собираться на Linux без изменений, кроме, возможно,
  `SIGPIPE`-специфики (см. «Принятые решения»).

## Структура проекта

```
kvdb/
├── CMakeLists.txt
├── src/
│   ├── thread_pool.hpp / .cpp   # пул потоков
│   ├── task.hpp                 # move-only замена std::function
│   ├── socket.hpp / .cpp        # RAII-обёртка над файловым дескриптором
│   ├── tcp_server.hpp / .cpp    # accept-цикл, self-pipe для остановки
│   ├── utils.hpp                # throw_errno и общие мелочи
│   └── main.cpp
├── tests/
│   ├── CMakeLists.txt
│   ├── test_thread_pool.cpp
│   ├── test_task.cpp
│   ├── test_socket.cpp
│   └── test_tcp_server.cpp
└── build/                       # вне репозитория, создаётся локально
```

`.hpp` и `.cpp` держатся рядом в `src/`, без разделения на `include/` —
проект собирает исполняемый файл, а не публичную библиотеку, разделение
API от реализации здесь не несёт пользы.

## Сборка

Несколько типов сборки, каждый в своей директории — CMake с генератором
Makefiles не умеет переключать конфигурацию в одной директории без
переконфигурации.

```bash
# обычная отладочная сборка
cmake -B build/debug -DCMAKE_BUILD_TYPE=Debug
cmake --build build/debug

# сборка с ThreadSanitizer — обязательна перед тем, как считать
# многопоточный код готовым
cmake -B build/tsan -DCMAKE_BUILD_TYPE=TSan
cmake --build build/tsan

# сборка с AddressSanitizer + UBSan — для RAII-классов и работы с
# сырыми дескрипторами/указателями
cmake -B build/asan -DCMAKE_BUILD_TYPE=ASan
cmake --build build/asan
```

`-fsanitize=thread` и `-fsanitize=address` несовместимы в одной сборке,
отсюда и разделение на типы.

### Тесты

```bash
ctest --test-dir build/debug --output-on-failure
ctest --test-dir build/tsan  --output-on-failure
```

Каждый тест зарегистрирован в CTest индивидуально (`gtest_discover_tests`)
и имеет таймаут — зависание из-за потерянного уведомления или deadlock
становится явным провалом, а не бесконечным ожиданием CI.

### Запуск

```bash
./build/debug/kvdb
```

По умолчанию слушает порт `8888`. `Ctrl+C` останавливает сервер штатно —
через `SIGINT` → self-pipe → выход из `accept`-цикла → корректное
закрытие всех дескрипторов через RAII.

## Архитектура

```
main
 └─ TcpServer::run(pool, handler)
     ├─ accept() новых соединений (через poll, вместе с self-pipe)
     └─ на каждое соединение: pool.submit(Task)
                                  └─ handler(Socket) выполняется в воркере
```

`TcpServer` не знает о протоколе БД — он принимает соединения и передаёт их
в обработчик, переданный снаружи. Разбор команд и хранилище подключаются
на уровне обработчика, а не самого сервера.

## Принятые решения

Раздел ведётся по мере разработки: по несколько строк на решение, которое
имело реальную альтернативу и было отвергнуто осознанно. Смысл — не
забыть аргументацию через месяц.

### Thread pool: `call_once` вместо атомарного флага в `shutdown()`

Атомарный флаг с ранним выходом (`if (exchange(true)) return;`) ломает
контракт: второй вызывающий возвращается мгновенно, не дожидаясь, пока
первый действительно доджойнит воркеров. Это опасно, если второй вызов —
из деструктора: объект может начать разрушаться, пока потоки ещё живы.
`std::call_once` гарантирует, что все вызывающие дождутся завершения
активного вызова, а не просто пропустят повторное исполнение.

### Проверка на self-join — до `call_once`, а не внутри

Если воркер сам вызывает `shutdown()`, а проверка на `get_id()` стоит
внутри тела `call_once`, возможен peaceful deadlock: главный поток —
активный исполнитель, джойнит воркеров; воркер зовёт `shutdown()` и
блокируется на `once_flag`, ожидая завершения активного вызова, который
ждёт этого самого воркера. Проверка обязана идти до входа в `call_once`.

### `Task` вместо `std::function<void()>`

`std::function` требует, чтобы хранимый объект был копируемым — это
свойство самого контейнера, а не прихоть реализации. Лямбда, захватившая
`Socket` (move-only по построению, чтобы избежать двойного `close()`),
копируемой не является. Вариантов было три: `std::shared_ptr<Socket>` в
захвате (обходит проблему ценой размытого владения), `std::move_only_function`
из C++23 (недоступен в текущей версии Apple Clang) и собственный
type-erasure класс. Выбран третий — `Task`: `unique_ptr<Base>` +
шаблонный `Impl<F>`, копирование запрещается автоматически через
некопируемость `unique_ptr`. Шаблонный конструктор ограничен через
`requires`, иначе он перехватывает копирование/перемещение самого `Task`
как более подходящая перегрузка.

### Self-pipe вместо `shutdown()` на слушающем сокете

Поток, блокированный в `accept()`/`poll()`, нельзя разбудить обычной
переменной — она не существует для него, пока вызов не вернётся. Закрытие
слушающего сокета извне создаёт гонку (дескриптор может быть переиспользован
другим потоком между `close()` и попыткой `accept()`), а поведение
`shutdown(fd, ...)` на слушающем сокете отличается между macOS и Linux.
Self-pipe (`pipe()` + `poll()` на двух дескрипторах) переносим и не имеет
гонок: `stop()` пишет байт в `wake_write_`, `poll()` в `run()` видит
данные на `wake_read_` и выходит из цикла.

### `SO_REUSEADDR`, но не `SO_REUSEPORT`

`SO_REUSEADDR` решает конкретную проблему разработки — повторный запуск
сервера сразу после остановки, без ожидания истечения `TIME_WAIT`. Он не
позволяет двум процессам одновременно слушать один порт — это отдельная
опция, `SO_REUSEPORT`, и в проекте она не нужна.

### Порт 0 в тестах

`TcpServer(0)` просит ядро выбрать свободный порт, а `getsockname()`
после `listen()` сообщает, какой именно достался. Это делает тесты
независимыми друг от друга и безопасными для параллельного запуска
(`ctest -j`), в отличие от захардкоженного порта.

### Обработка исключений на границах потоков

И `ThreadPool::worker_thread`, и `TcpServer::run` оборачивают
пользовательский код (`task()`, `handler(...)`) в `try/catch`.
Исключение, покидающее функцию потока или деструктор, приводит к
`std::terminate()` независимо от того, насколько «неважной» кажется
задача — один необработанный запрос от клиента не должен ронять весь
процесс.

## Дальнейшие шаги

- Протокол (`SET`/`GET`/`DEL`) и in-memory хранилище под мьютексом.
- WAL: append-only лог команд и replay при старте.
- Шардинг по `hash(key) % N` с независимыми потоком и очередью на шард.
- Нагрузочный клиент-бенчмарк, сравнение пропускной способности до/после
  шардинга.
- Логгер с синхронизацией вывода (сейчас `std::cerr`).
